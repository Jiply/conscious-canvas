## **2025-10-18 - Map/Tile System Implementation**

### **Timestamp**: Saturday, October 18, 2025

### **Implemented By**: Jeremy Soo (with AI assistance)

### **Overview**

Complete implementation of the tile-based map system for the Conscious Campus simulation, inspired by NUS UTown Singapore layout. This forms the foundation for agent pathfinding, place-based activities, and real-time visualization.

## **1. Schema Design (`convex/schema.ts`)**

### **Tables Created**

#### **`map_settings`** (Singleton)

- **Purpose**: Global configuration for the tile grid
- **Key Fields**:
  - `gridWidth: 80` - Horizontal tile count
  - `gridHeight: 50` - Vertical tile count
  - `tileSize: 32` - Pixels per tile
  - `metersPerTile: 1` - Real-world scale (1 tile = 1 meter)
  - `version: 1` - Schema version for future migrations
  - `seed` - Random seed for reproducible generation
  - `lastRegeneratedAt` - Timestamp of last regeneration

**Design Decision**: Singleton table ensures consistent grid configuration across all clients. Grid size (80×50 = 4000 tiles) balances detail with performance.

#### **`map_tiles`** (4000 documents)

- **Purpose**: Individual tiles representing the campus terrain
- **Tile Types**:
  - `floor` - Indoor surfaces (inside buildings) ✅ Walkable
  - `wall` - Solid barriers (building perimeters) ❌ Not walkable
  - `door` - Entrances/exits ✅ Walkable
  - `grass` - Lawns and outdoor areas ✅ Walkable
  - `water` - Decorative water features ❌ Not walkable
  - `path` - Paved walkways connecting buildings ✅ Walkable
  - `void` - Boundary/empty space ❌ Not walkable

- **Key Fields**:
  - `x, y` - Tile coordinates (0-based)
  - `tileType` - One of the 7 types above
  - `isWalkable` - Boolean for pathfinding
  - `visualVariant` - 0-3 for visual diversity
  - `placeId` - Optional reference to associated place (for indoor tiles)
  - `metadata` - Optional biome, lighting data

- **Indexes**:
  - `by_coordinates` (x, y) - Fast spatial lookups (O(1))
  - `by_place` (placeId) - Get all tiles in a building
  - `by_type` (tileType) - Query by tile type
  - `by_walkable` (isWalkable) - Pathfinding optimization

**Design Decision**: Full grid storage in Convex DB (rather than static files) enables:

- Real-time tile updates (e.g., doors opening/closing)
- Dynamic map regeneration
- Server-authoritative state for multiplayer consistency
- Efficient spatial queries via indexes

**Data Volume**: 4000 tiles × ~150 bytes/doc ≈ 600KB total storage.

#### **`places`**

- **Purpose**: Named locations on campus (buildings, outdoor areas)
- **Key Fields**:
  - `kind` - Place type (dorm, lecture, cafe, library, quad)
  - `name` - Display name
  - `bounds` - Rectangle in tile coordinates {x, y, width, height}
  - `entrances` - Array of {x, y, facing} entry points
  - `capacity` - Max agents (optional)
  - `isIndoor` - Boolean for environmental context
  - `metadata` - Real-world inspiration, ambient sound

- **Indexes**:
  - `by_kind` (kind) - Query by place type

**Design Decision**: Places are first-class entities separate from tiles, enabling:

- Abstract location references for agents (e.g., "go to Library")
- Capacity management for crowd control
- Metadata for LLM context (e.g., "This is inspired by NUS ERC Library")

#### **`world_settings`** & **`observer`**

Pre-defined in requirements.md for observer-dependent time mechanics. Not modified in this implementation phase.

## **2. NUS UTown Singapore Inspiration**

### **Real-World Mapping**

**Scale**: NUS UTown ≈ 400m × 300m real area → 80×50 tiles (each tile ≈ 5m real-world equivalent, scaled to 1m for simulation)

**Landmark Mapping**:

| Real-World Location   | Simulation Name           | Kind      | Tile Bounds    | Size              |
| --------------------- | ------------------------- | --------- | -------------- | ----------------- |
| **ERC Library**       | Education Resource Centre | `library` | (55, 5) 20×15  | 300 tiles         |
| **Lecture Halls**     | Lecture Theatre Complex   | `lecture` | (10, 15) 15×13 | 195 tiles         |
| **Town Plaza**        | Town Plaza Café           | `cafe`    | (30, 20) 15×10 | 150 tiles         |
| **Central Green**     | Central Green             | `quad`    | (35, 32) 20×12 | 240 tiles (grass) |
| **Residential Halls** | Student Residence         | `dorm`    | (5, 35) 20×13  | 260 tiles         |

**Spatial Layout Philosophy**:

- **Library** (northeast): Quiet study area, away from social hubs
- **Lecture Hall** (west-center): Academic core, near dorm for easy access
- **Café** (center): Social hub, equidistant from all buildings
- **Quad** (center-south): Open gathering space, central location
- **Dorm** (southwest): Residential area, close to lecture hall

**Connecting Infrastructure**:

- Main horizontal path (2 tiles wide) at Y=25 connecting east-west
- Vertical paths linking dorm, café, and library
- Total path network: ~400 tiles

**Water Features**:

- Pond near library (4×3 tiles) - decorative, not walkable
- Fountain near café entrance (1 tile) - landmark

**Boundaries**:

- `void` tiles on all edges (perimeter) for visual boundary

## **3. Implementation Files**

### **`lib/mapTypes.ts`**

**Purpose**: TypeScript type definitions for client-side usage

**Key Exports**:

- `TileType` - Union of 7 tile types
- `Tile`, `Place`, `MapSettings` - Interfaces mirroring schema
- `Point`, `Rect`, `Entrance` - Geometry types
- `TILE_VISUALS` - Visual configuration lookup (colors, walkability)
- `DEFAULT_MAP_SETTINGS` - Default 80×50×32 configuration
- `UTOWN_PLACES` - UTown reference data for documentation

**Design Decision**: Separate type file allows sharing between client/server without importing Convex SDK in client code.

### **`lib/mapUtils.ts`**

**Purpose**: Pure utility functions for coordinate math and tile operations

**Key Functions**:

- **Coordinate Conversion**:
  - `coordsToIndex(x, y, gridWidth)` - 2D → 1D
  - `indexToCoords(index, gridWidth)` - 1D → 2D
  - `pixelToTile(px, py, tileSize)` - Screen pixels → tile coords
  - `tileToPixel(x, y, tileSize)` - Tile coords → pixels
  - `tileToCenterPixel(x, y, tileSize)` - Tile → center pixel

- **Boundary Checking**:
  - `isWithinBounds(x, y, gridWidth, gridHeight)` - Bounds validation
  - `isPointInRect(point, rect)` - Point-in-rectangle test
  - `rectsIntersect(rect1, rect2)` - Rectangle collision

- **Neighbors & Adjacency**:
  - `getAdjacentTiles(x, y)` - 4-directional neighbors (N, E, S, W)
  - `getAdjacentTiles8(x, y)` - 8-directional (includes diagonals)

- **Distance Metrics**:
  - `manhattanDistance(p1, p2)` - For grid-based pathfinding
  - `euclideanDistance(p1, p2)` - Straight-line distance
  - `chebyshevDistance(p1, p2)` - Diagonal distance

- **Region Operations**:
  - `getTilesInRegion(rect)` - Get all tiles in rectangle
  - `getPerimeterTiles(rect)` - Get outer edge (for walls)
  - `getInteriorTiles(rect)` - Get inner area (for floors)

- **Tile Utilities**:
  - `tileKey(x, y)` - Generate "x,y" string key
  - `parseTileKey(key)` - Parse key back to coords
  - `isWalkableTileType(tileType)` - Check tile walkability

- **Random Utilities**:
  - `seededRandom(seed)` - Deterministic RNG for reproducible generation
  - `randomInt(min, max, rng)` - Random integer
  - `randomElement(array, rng)` - Pick random array element

**Design Decision**: Pure functions (no side effects) make testing easy and enable use in both client and server contexts.

### **`convex/seedMap.ts`**

**Purpose**: Map generation logic inspired by UTown layout

**Key Function**: `initializeMap(seed?)`

**Generation Algorithm**:

1. **Base Grid** (4000 tiles):
   - Initialize all tiles as `grass` (walkable)
   - Assign pseudo-random visual variants

2. **Create Places**:
   - Insert 5 place definitions into `places` table
   - Store place IDs for tile association

3. **Generate Place Tiles**:
   - For each **indoor** place:
     - **Perimeter** → `wall` (not walkable) or `door` at entrances (walkable)
     - **Interior** → `floor` (walkable)
     - Associate all tiles with `placeId`
   - For **outdoor** places (quad):
     - All tiles remain `grass` (walkable)

4. **Add Connecting Paths**:
   - Horizontal main path (Y=25, 2 tiles wide)
   - Vertical paths linking dorm → café → library
   - Total ~400 path tiles

5. **Add Water Features**:
   - Pond near library (4×3 tiles, not walkable)
   - Fountain near café (1 tile, not walkable)

6. **Add Boundaries**:
   - All edge tiles → `void` (not walkable)

7. **Batch Insert**:
   - Insert tiles in batches of 500 to avoid rate limits
   - Progress logging every 500 tiles

**Performance**: Total generation time ~5-10 seconds for 4000 tiles.

**Design Decision**: Deterministic generation with optional seed enables:

- Reproducible maps for testing
- Potential procedural variation in future
- Debug-friendly (same seed = same map)

### **`convex/map.ts`**

**Purpose**: Public queries and mutations for map access

**Public Queries**:

- `getMapSettings()` - Get grid configuration (singleton)
- `getAllTiles(limit?)` - Get all tiles (use with caution!)
- `getTilesByRegion(x, y, width, height)` - **Viewport-based fetching** (efficient)
- `getTileAt(x, y)` - Get single tile
- `getPlaces()` - Get all campus locations
- `getPlaceById(placeId)` - Get specific place
- `getPlacesByKind(kind)` - Query by place type
- `getWalkableTiles()` - Get all walkable tiles (for pathfinding init)

**Public Mutations**:

- `initMap(seed?, force?)` - Initialize or regenerate map
  - Checks if map exists (returns early if not force)
  - Clears existing data if `force=true`
  - Calls internal `seedMap.initializeMap()`
  - Returns success status, tile/place counts

**Internal Mutations**:

- `updateTile(x, y, updates)` - Modify single tile properties
- `batchUpdateTiles(updates[])` - Bulk tile updates (for dynamic changes)

**Design Decision**:

- **Viewport-based queries** (`getTilesByRegion`) are the recommended approach for clients rendering the map, avoiding fetching all 4000 tiles unnecessarily.
- **Index-optimized lookups** via `by_coordinates` ensure O(1) tile access.
- **Force regeneration** allows resetting the map for testing/demos.

## **4. Usage Instructions**

### **Initializing the Map**

From a Convex client (React component):

```typescript
import { useMutation } from "convex/react";
import { api } from "@/convex/_generated/api";

function MapInitializer() {
  const initMap = useMutation(api.map.initMap);

  const handleInit = async () => {
    const result = await initMap({
      seed: "utown_demo_001", // Optional seed
      force: false, // Set to true to regenerate
    });
    console.log(result);
    // { success: true, tilesCreated: 4000, placesCreated: 5 }
  };

  return <button onClick={handleInit}>Initialize Map</button>;
}
```

### **Querying Map Data**

```typescript
import { useQuery } from "convex/react";
import { api } from "@/convex/_generated/api";

function MapViewer() {
  // Get map settings
  const settings = useQuery(api.map.getMapSettings);

  // Get tiles in viewport (efficient)
  const tiles = useQuery(api.map.getTilesByRegion, {
    x: 0,
    y: 0,
    width: 80,
    height: 50,
  });

  // Get places
  const places = useQuery(api.map.getPlaces);

  return (
    <div>
      <p>Grid: {settings?.gridWidth} × {settings?.gridHeight}</p>
      <p>Tiles loaded: {tiles?.length}</p>
      <p>Places: {places?.length}</p>
    </div>
  );
}
```

### **Using Map Utilities**

```typescript
import { pixelToTile, getTileKey, isPointInRect } from "@/lib/mapUtils";

// Convert mouse click to tile
const handleCanvasClick = (event: MouseEvent) => {
  const tileCoords = pixelToTile(event.offsetX, event.offsetY, 32);
  console.log(`Clicked tile: ${tileCoords.x}, ${tileCoords.y}`);
};

// Check if agent is inside a place
const place = { bounds: { x: 10, y: 15, width: 15, height: 13 } };
const agentPos = { x: 17, y: 21 };
const isInside = isPointInRect(agentPos, place.bounds);
console.log(`Agent in ${place.name}: ${isInside}`);
```

## **5. Design Decisions & Rationale**

### **Why Full Grid Storage in DB?**

**Alternative considered**: Static JSON file with pre-baked grid.

**Chosen approach**: Store all 4000 tiles in Convex DB.

**Rationale**:

- Enables **dynamic tile updates** (e.g., doors open/close, weather effects)
- **Server-authoritative** state ensures multiplayer consistency
- **Real-time sync** via Convex live queries (tiles update instantly across all clients)
- **Efficient queries** with spatial indexes (by_coordinates, by_walkable)
- **600KB total storage** is negligible for Convex

**Trade-off**: Slightly higher initial load vs. flexibility and real-time capabilities.

### **Why Multiple Tile Types?**

**Alternative considered**: Binary walkable/solid tiles.

**Chosen approach**: 7 distinct tile types (floor, wall, door, grass, water, path, void).

**Rationale**:

- **Visual richness**: Different colors/textures for each type
- **Gameplay variety**: Doors (interactive), water (decorative), paths (clear navigation)
- **LLM context**: Tile type informs agent behavior (e.g., "avoid water", "use paths")
- **Future extensibility**: Easy to add new types (e.g., "sand", "stairs", "elevator")

### **Why UTown Inspiration?**

**Rationale**:

- **Real-world authenticity**: Grounded in actual campus layout
- **Student familiarity**: NUS students will recognize landmarks
- **Spatial logic**: UTown's design balances academic/social/residential zones
- **Hackathon story**: "We simulated a real Singapore campus!"

### **Why 80×50 Grid?**

**Rationale**:

- **Scale**: 1 tile = 1 meter → 80×50 = 80m × 50m campus (reasonable size)
- **Performance**: 4000 tiles is manageable for Convex + Pixi.js rendering
- **Pathfinding**: A\* can handle 4000-node graphs efficiently
- **Resolution**: 32px tiles → 2560×1600px canvas (fits modern screens)

**Future consideration**: Could expand to 120×80 (9600 tiles) if needed.

## **8. Known Issues & Future Improvements**

### **Current Limitations**

1. **Single map instance**: No support for multiple map instances (yet)
2. **No undo/redo**: Map regeneration is destructive
3. **No visual preview**: Must render in Pixi to see layout
4. **Hardcoded paths**: Path network is not procedurally generated

### **Potential Optimizations**

1. **Chunk loading**: Load tiles in 16×16 chunks for better caching
2. **Sparse storage**: Only store non-default tiles (compress grass tiles)
3. **Tile compression**: Use bit flags for tile properties (reduce storage)
4. **Spatial hashing**: Pre-compute spatial hash for faster neighbor queries

### **Future Features**

1. **Multi-floor buildings**: Add Z-coordinate for elevators/stairs
2. **Dynamic weather**: Rain affects tile walkability (slippery)
3. **Destructible tiles**: Walls can be removed/added dynamically
4. **Map editor UI**: Visual tool for custom map creation
